## 1. P0 —— 先用起来最疼的四条

### U1. 深色主题下，文件列表是「黑字深底」（基本不可读）

**现象**：切到深色主题，文件列表的文件名 / 副标题 / `..` 行显示为近黑色，背景 `#121212`，
对比度≈1:1，等于看不见。浅色主题一切正常，所以日常可能一直没暴露。

**证据（代码是确定的）**：
- 文件名：`app/src/main/kotlin/com/u707t/panelfm/ui/browser/PaneView.kt:683`
  `color = (if (item.isHidden) MtSpec.RowSubLight else MtSpec.RowNameLight)` → `RowNameLight = 0xEE000000`（近黑）
- 副标题：`PaneView.kt:690` `color = MtSpec.RowSubLight.copy(...)` → `0x99000000`（深灰）
- `..` 行：`PaneView.kt:466` `color = MtSpec.RowNameLight`
- 选中勾：`PaneView.kt:699` `tint = MtSpec.AccentLight`（深色下应 `AccentDark`）
- 深色主题背景：`core/ui/.../Theme.kt:51` `background = Color(0xFF121212)`，
  整屏铺底在 `app/.../ui/AppRoot.kt:209`。
- 讽刺的是**深色常量早就写好了但没人用**：`MtSpec.RowNameDark = 0xEED0D0D0`、
  `RowSubDark = 0x99C4C4C4`（`MtSpec.kt:114/118`），全仓使用点 **0**。

**修法**（二选一）：
1. 直接换成主题感知色：`MaterialTheme.colorScheme.onSurface` / `onSurfaceVariant` / `primary`
   （`Theme.kt` 里深色方案已经把它们定义成 MT 的深色值，改完自动正确）；
2. 或按 `dark` 分支取 `RowNameDark/RowSubDark/AccentDark`。

**顺带一起修**（同一根因：拿「系统深色」当「应用主题」用）：
- `PaneView.kt` 的 `val dark = isSystemInDarkTheme()`（MtFileRow 内，选中底色用）、
  `DualPaneScreen.kt:303`（顶栏底色）、`SideDrawer.kt:108/138`（抽屉头部）。
  用户「应用内选浅色、系统是深色」（或反之）时这些会取错分支。
  建议在 `PanelTheme` 里提供 `LocalPanelDarkColorScheme` 之类的标志，全项目统一读它。

**验收**：深色主题下文件名/副标题清晰可读；抽屉标题 #666666（`SectionTitleLight`，
`Components.kt:106`）也偏暗，可顺手调亮。

### U2. 返回键永远退不出 App；「再按一次退出程序」是死设置

**现象（真机一分钟可复核）**：
- 在浏览器根目录按返回 → **切到主页**；在主页按返回 → **回到浏览器**；来回循环，**退不出去**。
- 设置里打开「退出前双次确认」→ 没有任何作用（永远不触发）。
- 唯一的退出方式：浏览器右上 `⋮` → 「退出」（`DualPaneScreen.kt:818` `finishAffinity()`），藏得深。

**机制（不猜，代码可复核）**：
- `AppRoot.kt:71` 导航栈初始 `[Screen.Browser]`；`:74` 返回=`pop()`、`:79` 返回=退出确认
  （`enabled = stack.size <= 1 && confirmExit`）。
- `DualPaneScreen.kt:240` 自己又注册了一个 `BackHandler(enabled = true)`，它的组合顺序
  晚于 AppRoot 的两个 → 按 `OnBackPressedDispatcher`「后注册先收到」的规则，**只要浏览器在顶层，
  所有返回键都先到它**；其 `else` 分支（`:256`）执行 `onOpenHome()` →
  `AppRoot.kt:215 push(Screen.Home)`。
- 于是「退出确认」那个 BackHandler 永远排在后面，永远轮不到。
- 另一个死代码：`DualPaneScreen.kt:243-249`「再按一次返回上级」分支不可达
  （外层要求 `parent != null || archive`，内层要求 `parent == null && !archive`，恒 false），
  配套的 `upArmed` 状态也是死的。

**修法（建议设计）**：
1. `DualPaneScreen` 的 BackHandler 改成**只在有内部目标时启用**：
   `enabled = drawerState.isOpen || focused.loading || focused.hasSelection || canGoUp`；
2. 没有内部目标时把返回键让给 AppRoot 的退出流程：根目录 / 主页 → 按 `confirmExit`
   决定「连按两次退出」还是「直接退出（或 moveTaskToBack）」；
3. 删掉 `upArmed` 死分支（或真正实现「已在最上级 → 再按一次返回上级」语义）；
4. 「退出」保留在 ⋮ 菜单不冲突。

**验收**：主页与浏览器根目录按一次返回不再互相跳；开「双次确认」后连按两次能退出；
关掉后单击返回能退出（或按你想要的习惯 moveTaskToBack）。

### U3. 所有输入对话框都不自动聚焦、不弹键盘；键盘也没有「完成」提交

**现象**：点「重命名 / 新建文件夹 / 新建文件 / 跳转路径 / 过滤 / 压缩包内重命名 / 搜索…」，
对话框出来后**必须再点一下输入框**才能打字；打完字**不能用键盘回车提交**，得移动手指去点按钮。
这些恰恰是文件管理器最高频的操作。

**证据**：
- 全仓 `FocusRequester` 命中数 **0**（`grep -rn "FocusRequester" app core`）；
- `Dialogs.kt:148 TextInputDialog`（承载重命名/新建/跳转/过滤）就是裸 `OutlinedTextField`；
- 其它同类：`SearchDialog.kt:93` 起、`Dialogs.kt` 的 `MtCompressDialog` 文件名、
  `SettingsScreen.kt` 的 UA 编辑、`ToolsScreens.kt` 的 Apps 搜索。

**修法**：
- 进入对话框：`LaunchedEffect(Unit) { focusRequester.requestFocus() }`，并
  `LocalSoftwareKeyboardController.current?.show()`；
- 加 `KeyboardOptions(imeAction = ImeAction.Done/Search)` + `KeyboardActions(onDone = 同「确定」)`；
- 对话框内容加 `Modifier.imePadding()`（App 已是 `adjustResize`，但 Dialog 是独立窗口，
  要实机确认键盘不遮按钮）。

**验收**：打开「重命名」键盘自动弹出；输入后按回车直接完成。

### U4. 耗时操作全程「没反应」：压缩 / 完整性测试 / 校验值 / 目录对比 / 打开远程压缩包

**现象**：这些操作开始后没有任何进度、没有取消入口，用户看着界面像卡死：

| 操作 | 现状 | 证据 |
|---|---|---|
| 压缩（GB 级目录） | 只在开始/结束各弹一次 3 秒 snackbar，中间无进度、无取消 | `BrowserController.kt:502` `onProgress = { _, _ -> }`（空实现，`compressToOther`）；`compressHere` 连回调都不传（`:1711` 起） |
| 压缩包完整性测试 | 全包逐条读校验，结束才出结果 | `BrowserController.kt:1109` 起 `testArchive` |
| 校验值 CRC32/MD5/SHA | 算完才弹结果，大文件期间零反馈 | `BrowserController.kt:1809` 起 `checksum` |
| 目录对比 | 只 showStatus，结束后才弹结果框 | `BrowserController.kt:1596` 起 `compareDirectories` |
| 打开远程压缩包 | 静默把整包下载到 cache 再挂载；**无提示、无取消**；且缓存登记在下载完成之后 | `BrowserController.kt:443` 起 `openArchiveInPane` + `AppContainer.kt:335` 起 `openArchive` |

**附带风险**：`openArchive` 里 `archives[host.toString()]` 在下载完成之后才写入 ——
用户看不到进度会连点两次，**两个协程并发下载/写同一临时文件**，可能写出坏缓存。

**修法**：
- 统一给「长操作」一个可以看见的状态：进度 + 取消（压缩/完整性测试可以直接复用任务行，
  或者用加载遮罩的老范式）；至少在页面里放一个不可消失的状态条；
- `openArchive` 对同一 host 做「in-flight 去重」（`ConcurrentHashMap<host, Deferred>`），
  并显示「正在下载压缩包（xx MB）…」。

**验收**：压缩 1GB 文件夹能看到百分比、能取消；打开 500MB 远程 zip 立刻有进度；
连点两次不会并发下载。

### U5. 点「停止搜索」会误报「搜索失败：…」，并把「已停止搜索」顶掉

**证据**：`DualPaneScreen.kt:1055-1073`：

```kotlin
val outcome = runCatching { controller.searchTree(...) }
    .onFailure { controller.showStatus((it as? VfsException)?.userMessage ?: "搜索失败：${it.message}") }
    .getOrNull()
```

`searchJob.cancel()`（「停止搜索」按钮，`:1093-1096`）→ `searchTree` 抛 `CancellationException`
→ **`runCatching` 把它也当失败** → 弹出「搜索失败：Job was cancelled」，并覆盖刚才的
「已停止搜索（已找到 N 条）」。

**修法**：`onFailure` 里先判 `if (it is CancellationException) return@onFailure`（或改 try/catch，
先 catch CancellationException 再 rethrow）。顺手把项目里其它 `runCatching` 包可取消协程的地方
也过一遍（同类隐患：后台操作被取消时的假报错）。

**验收**：搜索中点「停止搜索」→ 只出现「已停止搜索」。

### U6. 「保存时自动 .bak 备份」从第二次保存起**静默失效**

**证据**：
- `EditorScreen.kt:867-869`：`runCatching { vfs.rename(uri, uri + ".bak") }` —— 失败被吞掉，无提示；
- `LocalVfs.kt:191`：`if (dst.exists()) throw VfsException.Conflict(to)` ——
  `x.bak` 已存在时 rename 必然失败。
- 所以：第一次保存生成 `x.bak`；**第二次保存起因为 `x.bak` 已存在，备份不再生成/更新**，
  用户以为一直有备份，其实没有。
- 附带：第一次保存是「先改名再写新文件」，若写入失败，目录里只剩 `x.bak`（原名消失）。

**修法**：备份改成「复制」而不是「改名」，且目标名带序号/时间戳（`x.bak`、`x.bak.1`…）或
先查重名；失败要提示；写新内容与备份的顺序调整（先写临时文件，成功后再滚动备份）。

**验收**：连按两次保存，每次都有新的备份文件，且失败时有提醒。

### U7. 破坏性操作没有二次确认 / 有静默覆盖

1. **回收站「清空」**（`ToolsScreens.kt:67` `purgeAll()`）与**「彻底删除」**（`:98`）——单击即执行，
   没有确认。普通删除都有确认框，这两处更不可逆反而没有。
2. **任务「取消」「移除」**（`TasksScreen.kt:98/100`；浏览器任务条的「取消」）——无确认。
   「移除」还会静默取消任务；被取消的传输会留下隐藏 `.part`（见 U13）。
3. **导出 APK**（`ToolsScreens.kt:170`/`:181 exportApk`）：
   - 无进度（动辄 50–300MB）；
   - 目标名固定 `$label.apk`，`LocalVfs.commit()` 是「**先删同名再改名**」
     （`LocalVfs.kt:375-378`）→ **静默覆盖**已有文件；
   - 跑在 `rememberCoroutineScope` → **离开页面即取消**，无提示，且不调 `abort()` → 留下 `.part`。

**修法**：清空/彻底删除/任务取消加确认；导出加进度 + 同名自动 `(1)` 或询问 + 完成/失败全局提示。

**验收**：清空回收站会先问；导出一个已存在同名 APK 不会默默覆盖。

### U9. Snackbar 只有 3 秒、还会互相覆盖

**证据**：`DualPaneScreen.kt:1420` `delay(3000); consumeStatus()`；无队列 —— 新消息直接替换旧消息；
`HomeScreen.kt:388` 是 4 秒。

**影响**：批量重命名「完成 x/y」、压缩失败原因、完整性检查结果、删除部分失败……都可能
在用户看到前消失，或被下一条操作的状态顶掉。

**修法**：错误/结果类信息改用对话框（`MessageDialog` 已有）或可回看的状态面板；
至少做到：**错误不自动消失**、消息放队列不互相顶。

**验收**：制造「压缩失败」，紧接着点一下别的东西，错误提示仍然能被看到。

### U10. 进程被回收 / Activity 重建后：导航栈全丢、编辑器草稿全丢

**证据**：
- `AppRoot.kt:71` `var stack by remember { ... }`；全仓 `rememberSaveable` 命中 **0**。
- 触发场景（不用等低内存）：开发者选项「不保留活动」、字体大小/密度等未在
  `configChanges` 列表里的变更、系统回收后台进程。重建后：
  - 导航栈回到浏览器首页（预览/编辑器/设置全关）；
  - **编辑器未保存文本直接消失**（`EditorScreen.kt:94-114` 全是 `remember`，无提示无草稿）。

**修法**（按性价比排序）：
1. 编辑器：草稿落盘（`PrefsStore`/cache 临时文件）或 `onSaveInstanceState`，重建时恢复并提示「已恢复未保存内容」；
2. 导航栈用 `rememberSaveable`（`Screen` 存轻量字符串编码；预览/编辑页可通过 URI 重建）；
3. 至少让 App 冷启后「上次未完成的任务/编辑」有迹可循。

**验收**：开「不保留活动」→ 打开编辑器改两行 → 切后台 → 回来：现在必丢；修好后至少不静默丢。

## 3. P2 —— 小体验修补（可批量做）

1. **U11 远程管理 URL 不能复制**：`ToolsScreens.kt:255` 只是 `Text(url)`（不可选中）。
   用户在电脑上要手输这个地址 —— 加一个「复制」按钮（顺手可加二维码）。`SelectionContainer` 也行。
